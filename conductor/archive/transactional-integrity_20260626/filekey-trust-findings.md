# fileKey Trust Gap Investigation

## Scope

Investigation only — no implementation in Track 8.3.

## Current Flow

1. `getPresignedUploadUrl` (`src/server/files.server.ts`)
   - Validates that the checkpoint exists, belongs to the student, and is in a submittable state (`unlocked` or `revise`).
   - Validates `extension` and `contentType` via `validateUploadType()`.
   - Generates a server-side UUID-based key: `generateFileKey(extension)` → e.g. `submissions/{uuid}.{ext}`.
   - Returns `{ uploadUrl, fileKey }`.
2. Client PUTs the file bytes directly to the presigned `uploadUrl`.
3. `submitCheckpoint` (`src/server/submissions.server.ts`)
   - Validates the checkpoint again (ownership, state, file size/name, verified consultations).
   - Inserts a `submissions` row using the `fileKey` string supplied by the client in the request body.

## Trust Gap

`submitCheckpointHandler` does not verify that the provided `fileKey`:

- Was generated by `getPresignedUploadUrlHandler` for this exact `(student, checkpoint)` pair.
- Actually corresponds to a file that was uploaded to the generated presigned URL.

Because the presigned URL is not bound to a specific `checkpointId` or `studentId`, and because there is no server-side record linking a generated `fileKey` to the context in which it was created, a client could:

- Submit a `fileKey` generated for a different checkpoint or a different student.
- Reuse a `fileKey` that was never uploaded, or reuse a `fileKey` already assigned to another submission row.
- Swap file keys with another student.

The handler only validates that the *format* of the string is plausible (`validateUploadFileName`) and that the checkpoint/s student gating is satisfied. It does not close the gap between presign-time authorization and submit-time consumption.

## Feasibility of a Presign-Time Mapping Table

A dedicated mapping table would close the gap:

```text
pending_uploads
  id             uuid PK        -- equals the generated fileKey
  checkpoint_id  integer        -- FK to checkpoints
  student_id     text           -- user who requested the presign
  extension      text
  content_type   text
  created_at     timestamp
  expires_at     timestamp
  used_at        timestamp nullable
```

### Flow With Mapping Table

1. `getPresignedUploadUrlHandler` inserts a `pending_uploads` row with the generated `fileKey`, the validated `checkpointId`, and `studentId`. The returned `fileKey` is the authoritative token.
2. Client uploads to R2.
3. `submitCheckpointHandler` replaces the bare `fileKey` parameter check with:
   - Select from `pending_uploads` where `id = fileKey`, `checkpoint_id = checkpointId`, `student_id = session.user.id`, and `used_at IS NULL`.
   - Reject with 400/404 if the mapping is missing, mismatched, or already used.
   - Inside the same transaction that inserts the submission, update `pending_uploads.used_at = now()`.

### Pros

- Strong binding between presign authorization and submit consumption.
- Prevents key reuse and cross-checkpoint key substitution.
- Enables expiration/cleanup of unused presigned keys.

### Cons

- Adds a new state table and cleanup job (expired rows).
- Requires a migration and schema change.
- Slightly more complex submit handler (one extra write in the transaction).

## Recommended Approach

1. **Track 8.x follow-up**: Implement the `pending_uploads` mapping table and bind `submitCheckpoint` to presign-time authorization.
2. **Until then as a tactical control**: Enforce that `fileKey` matches a strict UUID regex and prefix (`submissions/` or `feedback/`), and query `submissions` to reject a `fileKey` that already exists (prevents reuse). This is weaker than the mapping table but blocks the most obvious replay attack.

## Out of Scope for Track 8.3

No code changes for `fileKey` trust were made in this track; findings recorded for a future track.
