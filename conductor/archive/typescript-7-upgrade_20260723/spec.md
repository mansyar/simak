# Track: TypeScript 7 Upgrade

## Overview

Upgrade the SIMAK project from TypeScript 5.8 to TypeScript 7.0 — the native Go port of the TypeScript compiler. TypeScript 7.0 GA was released July 8, 2026 and ships as the standard `typescript` npm package under the `latest` tag.

The project is a low-risk upgrade candidate: it has zero direct imports of the `typescript` package (no Compiler API consumers), no blocked frameworks (pure React + TanStack Start, no Vue/Svelte/Astro/MDX/Angular), and uses oxlint (not typescript-eslint) so the linter is unaffected. The only tsconfig blocker is `baseUrl: "."`, which was removed in TS 7.

**Type:** Chore (infrastructure/tooling upgrade)
**Estimated Effort:** ~1 Day
**Risk Level:** Low

## Background & Audit Summary

TypeScript 7.0 is a native Go rewrite of the compiler, delivering 8-12x faster full builds with shared-memory multithreading. The type-checking logic is structurally identical to TS 6.0 (bug-for-bug compatibility). All breaking changes are config-level (removed/changed compiler options), not type-system changes.

Key audit findings:
- **Zero Compiler API consumers** — confirmed via grep across all `.ts/.tsx/.js/.mjs/.cjs` files. The biggest blocker for most projects does not apply.
- **No blocked frameworks** — no Vue/Svelte/Astro/MDX/Angular. typescript-eslint is not used (oxlint has its own Rust-based parser).
- **tsc is type-checking only** (`tsc --noEmit --incremental`). Transpilation is handled by Vite/esbuild. No emit path, no downleveling.
- **tsconfig.json** — only `baseUrl: "."` must be removed (removed in TS 7). The path alias `"@/*": ["./src/*"]` is already relative to the project root, so removing `baseUrl` has zero functional impact. All other options (`strict: true`, `module: "ESNext"`, `target: "ES2022"`, `moduleResolution: "Bundler"`, `esModuleInterop: true`, `types: ["vitest/globals", "node"]`) are already TS 7-compatible.
- **`noUncheckedSideEffectImports`** defaults to `true` in TS 7 — may surface side-effect import typos (beneficial, not a blocker).

## Functional Requirements

### FR-1: Remove `baseUrl` from tsconfig.json
Remove the `baseUrl: "."` line from `tsconfig.json`. This option was removed in TS 7. The existing `paths` mapping (`"@/*": ["./src/*"]`) is already relative to the project root, so no path alias changes are needed.

### FR-2: Upgrade TypeScript package
Update `typescript` from `^5.8.0` to `^7.0.0` in `package.json`. Run `pnpm install` to update the lockfile.

### FR-3: Delete stale incremental cache
Delete `tsconfig.tsbuildinfo` before the first TS 7 run. The incremental cache format is incompatible between major versions.

### FR-4: Update tech-stack.md
Document the TypeScript version change in `conductor/tech-stack.md` with a dated changelog entry, as required by the project workflow ("Changes to the tech stack must be documented in tech-stack.md before implementation").

### FR-5: Tune CI typecheck with `--checkers` flag
Add the `--checkers` flag to the pre-push typecheck gate in `lefthook.yml` (and any CI configuration) to leverage TS 7's shared-memory multithreading. The default is 4 worker threads; this may be tuned based on available cores.

### FR-6: Verify full quality gate suite
Run and confirm all quality gates pass under TS 7:
- `pnpm typecheck` — `tsc --noEmit --incremental`
- `pnpm test` — unit tests (excludes integration)
- `pnpm test:coverage` — coverage ≥80% on all four metrics
- `pnpm lint` — oxlint (including `simak-i18n/no-hardcoded`)
- `pnpm check:i18n` — i18n key parity EN↔ID
- `pnpm build` — full production build (i18n codegen + vite build + migrate/seed bundles)
- `pnpm generate:i18n` — i18n type generation

## Non-Functional Requirements

### NFR-1: No behavioral changes
The upgrade must not change any runtime behavior. TS 7's type-checking logic is structurally identical to TS 6.0 (bug-for-bug compatibility). The only expected differences are faster typecheck times and potentially new errors from `noUncheckedSideEffectImports` (which surfaces real bugs in side-effect imports).

### NFR-2: Typecheck performance improvement
Measure and document the typecheck speedup before/after the upgrade. TS 7 delivers 8-12x faster full builds; the `--incremental` typecheck should also see meaningful improvement.

## Acceptance Criteria

1. `tsconfig.json` no longer contains `baseUrl`.
2. `package.json` specifies `typescript: ^7.0.0`.
3. `tsconfig.tsbuildinfo` deleted (and regenerated by first TS 7 run).
4. `conductor/tech-stack.md` has a dated changelog entry documenting the TS 7 upgrade.
5. `lefthook.yml` pre-push typecheck command includes `--checkers`.
6. All quality gates pass: `pnpm typecheck`, `pnpm test:coverage`, `pnpm lint`, `pnpm check:i18n`, `pnpm build`.
7. Typecheck speedup measured and documented (before/after).
8. `pnpm dev` starts successfully (i18n codegen runs, Vite dev server boots).

## Out of Scope

- **TypeScript 7.1 programmatic API** — TS 7.0 ships without a stable programmatic API; no project code consumes the Compiler API today, so this is irrelevant.
- **`@typescript/typescript6` compatibility package** — not needed; no code uses the TS Compiler API.
- **`--builders` flag tuning** — for parallel project reference builds; this project has a single tsconfig with no project references, so `--builders` is not applicable.
- **Migration via TS 6.0 intermediate step** — direct 5.8→7.0 upgrade is safe given the audit findings; no intermediate step needed.
- **Formal rollback documentation** — git revert is sufficient for this small, low-risk change.
- **Code changes beyond config/tooling** — no source code modifications expected. If `noUncheckedSideEffectImports` surfaces issues, they will be addressed as bug fixes within this track.
